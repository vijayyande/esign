Certifying authority · port 8084

CA documentation

The ESP calls this service after eKYC succeeds. It issues a short-lived certificate for the signer name and signs each document hash. The end-entity private key is not stored.

Try the API

Choose an operation, change the fields, and send the call to this service. Issuing a certificate creates a real short-lived certificate. The end-entity private key is discarded after the response.

The response appears here.

The CA keystore is data/ca/ca.p12, password changeit. It is created on first start as a self-signed RSA 2048 certificate, subject CN=eSign Reference CA, O=eSign Reference, C=IN, with basic constraints CA and key usage keyCertSign and cRLSign. End-entity certificates last esign.certificate-validity-hours (default 24), use RSA 2048 or EC secp256r1, and have digitalSignature key usage only.

Issue a certificate

signingAlgorithm is RSA or ECDSA. Each document needs an id, a 64-character SHA-256 hex, and a response signature type. A bad hash or type is reported on that item and does not fail the other documents.

curl.exe -s -H "Content-Type: application/json" -d "{\"subjectName\":\"Demo Signer\",\"signingAlgorithm\":\"RSA\",\"documents\":[{\"id\":\"1\",\"hashHex\":\"2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824\",\"responseSigType\":\"PKCS7pdf\"}]}" http://localhost:8084/api/v1/certificates
{
  "certificateBase64": "DER of the end-entity certificate",
  "certificatePem": "-----BEGIN CERTIFICATE-----...",
  "caCertificateBase64": "DER of the reference CA",
  "signatures": [
    {
      "id": "1",
      "signatureBase64": "CMS or raw signature",
      "sigHashAlgorithm": "SHA256",
      "error": ""
    }
  ]
}

The subject is CN=<subjectName>, OU=eSign, O=eSign Reference CA, C=IN. A blank subject name, an empty document list, or an algorithm other than RSA or ECDSA is a request error:

{"errorCode":"101","errorMessage":"Invalid Request Format"}

No document is error 108.

Signature types

responseSigTypeWhat is returned
rawPKCS#1 DigestInfo for RSA, or ECDSA over the 32-byte hash
PKCS7Detached CMS with the signer certificate only
PKCS7pdfDetached CMS that also contains the CA certificate
PKCS7completeSame certificate set as PKCS7pdf in this reference

The CMS message-digest attribute is the precomputed SHA-256. The signed content bytes are empty, which matches a hash the ASP computed before the call. There is no OCSP or CRL responder, so the signature does not carry revocation data.

One bad item leaves the others usable. Here the second hash is too short, so its error is 201 and the first signature is still produced:

{
  "subjectName": "Demo Signer",
  "signingAlgorithm": "RSA",
  "documents": [
    {"id": "1", "hashHex": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824", "responseSigType": "PKCS7"},
    {"id": "2", "hashHex": "abcd", "responseSigType": "PKCS7pdf"}
  ]
}

An unknown responseSigType sets that item's error to 202.

Errors

This service uses JSON for issuance, so the HTTP status comes from the catalogue. Per-document problems stay in signatures[].error and the HTTP call still succeeds. The full list is /api/v1/meta/error-codes.

CodeWhen
101Missing subject name, or signing algorithm is not RSA or ECDSA
108No documents were supplied
201That document's hash is not 32 bytes of hex
202That document's response signature type is not raw, PKCS7, PKCS7pdf, or PKCS7complete
199The certificate could not be built
